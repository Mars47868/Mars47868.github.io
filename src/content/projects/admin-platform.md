## 問題背景

客戶要的是一套能自己維護商品資料的後台，加上一組給合作端呼叫的對外查詢 API。客戶有自己的架構規範：資料層指定 jOOQ 搭配 code generation，不用 JPA / Hibernate。

需求本身不複雜，難的是三件會在上線後才咬人的事：多表寫入中途失敗時，資料不能只寫一半；查詢 API 要快，但後台一改資料就得立刻生效；呼叫端行為不受控，資料庫不能被打垮。

客戶名稱與業務邏輯受保密協議約束，本文只談技術棧與設計決策。

## 解決方案

- **交易一致性**：找到 `@Transactional` 靜默失效的根因並修掉，多表寫入任一步失敗整筆回滾，並以 rollback 測試鎖住這個行為
- **條件式快取**：查詢條件即 cache key、篩選條件下推到 SQL；Caffeine 以 weigher 按實際位元組設記憶體上限；後台編輯與排程同步時主動清快取，資料異動立即對外生效，不依賴 TTL
- **四層限流**：全域節流 → 呼叫端並發 → 每日上限 → 短期速率，各層獨立錯誤碼、檢查順序固定，呼叫端能自行判讀被擋原因；全域參數外部化到設定檔
- **技術棧**：Spring Boot 2.7（Java 11）、jOOQ code generation、MariaDB、Thymeleaf、AngularJS 管理後台、Docker Compose

## 我的角色與做法

- **獨立開發、單一對口**：需求釐清、架構與資料庫設計、前後台開發、測試到交付，全程一人；客戶的架構回饋由我逐項對照程式碼回覆並修正。
- **測試隔離**：43 個測試類別、265 個單元測試跑在專用 schema，打包流程不會對正式資料執行破壞性測試。
- **區分客戶約束與自己的決策**：jOOQ 是客戶規範，不是我的選型；交易修法、快取策略與限流設計才是我的判斷，對客戶說明時兩者分開講。

## 技術決策

**快取不賭 TTL。** 用 TTL 等於在「資料過期多久能接受」上押注，而後台編輯與排程同步正好是唯二會改資料的地方。把清快取掛在這兩個點上，資料一改立刻生效，TTL 只留作保底。Caffeine 的上限按位元組而不是按筆數算，因為單筆資料大小差異很大，按筆數估不準記憶體。

**限流分層、錯誤碼分開。** 單一閾值擋得住流量，但呼叫端被擋時只會看到一個 429，不知道是並發太高還是今日額度用完。四層各自回不同錯誤碼、檢查順序固定，合作端可以自己排查，減少來回溝通。

**排序欄位改走白名單。** 整理 DataTables 伺服器端分頁時，把排序欄位從直接拼進 SQL 改為白名單對照，順手關掉一個 SQL injection 風險。

## 挑戰與踩坑

最大的坑是 `@Transactional` 看起來有效、其實沒有。

程式能跑、標註也有、沒有任何錯誤，但多表寫入故意讓第二步失敗時，第一步的資料還是留在資料庫裡。追下去才發現：jOOQ 直接向連線池取連線，根本不在 Spring 的交易上下文裡，Spring 開的交易和 jOOQ 用的連線是兩回事。

修法是把 DataSource 用 `TransactionAwareDataSourceProxy` 包一層，讓 jOOQ 拿到的是 Spring 交易管理下的連線；當時用的 jOOQ 3.14 沒有現成的 Spring transaction provider，先自己寫了一個，後來改用 Spring Boot 官方整合機制取代，少維護一段自製程式。這個 bug 沒有任何症狀，只有寫了 rollback 測試才抓得到，所以那支測試被留在套件裡當回歸守門。

另一個小坑是 DataTables 伺服器端分頁被每張表各寫一份，抽成共用 helper 時一併修掉三個潛藏問題：搜尋條件沒有實作、`draw` 欄位被多加一、`recordsTotal` 從未賦值。
